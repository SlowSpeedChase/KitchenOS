# Filter Cook Now by meal type

**Status:** Ready for Implementation · **Branch:** `cook-now-meal-type-filter` · **Date:** 2026-07-25

## Problem

Reviewing "what could I cook right now?" surfaces 47 dessert recipes mixed in with dinner
candidates. There is no way to narrow the list by meal type.

Two things block a filter:

1. **Cook Now has no web surface.** `lib/cook_now.py:131` writes a generated vault note
   (`Cook Now.md`), regenerated by `generate_meal_plan.py:209`, `ingest_receipts.py:141`,
   and `scripts/update_dashboard_canvas.py:81`. There is no route and no API endpoint — a
   static note cannot be filtered interactively.

2. **`dish_type` is too noisy to filter on.** It is present on all 239 recipes and is the
   right field (`main` 77, `dessert` 47, `breakfast` 21, `salad` 15, `snack`/`appetizer`/
   `side` 12 each, `drink` 10, `sauce` 7, `sandwich`/`soup`/`bread` 4 each), but:

   - **12 recipes carry one-off values** that would each become a junk singleton chip:
     `Dinner` (2), `Tostada`, `Shakshuka`, `biscuits`, `mocktail`, `Breakfast Pastry`,
     `savory pie`, `smoothie mix`, `pasta alternative`, `Salad dressing`,
     `dessert or snack`.
   - **The dessert bucket is contaminated.** `lib/normalizer.py:196` maps
     `"biscuit" → "dessert"`, so `Butter Biscuits` is filed as a dessert. The five biscuit
     recipes are spread across five different dish types (`dessert`, `biscuits`, `bread`,
     `side`, `breakfast`). Filtering desserts out would hide savory biscuits *and* leave
     other non-desserts in.

A filter built on this field without repairing it would be quietly wrong in both
directions, which is worse than no filter.

## Approach

Repair the data first, then build the filter on top of it. The cleanup is a one-off LLM
pass rather than a hand-written mapping of the 12 strays, because a hand mapping fixes only
the values we happened to enumerate and does nothing about the contaminated dessert bucket
— `Butter Biscuits` is stored as `dessert` and looks perfectly well-formed.

Decisions, and what they ruled out:

| Decision | Rejected alternative |
|---|---|
| Repair `dish_type` in the vault, then filter | Read-time bucketing only — leaves `Butter Biscuits` a dessert forever |
| LLM reclassification of all 239 recipes | Hand-mapping the 12 visible strays; only re-checking the 47 desserts |
| Dry-run diff report, `--apply` as a second explicit step | Writing straight to frontmatter on a single run |
| 13-value stored vocabulary, 6 UI chip groups | Chips bound 1:1 to stored values (24 chips, 12 of them singletons) |
| New `/cook-now` page + API, note left untouched | Sectioning the generated note; excluding desserts via config |
| Client-side chip filtering from one payload | A round trip per chip toggle |

The generated `Cook Now.md` note is deliberately left exactly as-is. Its three callers keep
working unchanged; the page is additive.

## Design

### Part 1 — Repair `dish_type`

**1. Controlled vocabulary.** Add `VALID_DISH_TYPES` to `lib/normalizer.py`, beside the
existing `VALID_MEAL_OCCASIONS`, with 13 values:

```
main  breakfast  side  salad  soup  sandwich  bread
snack  appetizer  dip  dessert  drink  sauce
```

These are exactly the values `DISH_TYPE_MAP` already treats as canonical (its
left-hand-side identity entries), so the vocabulary describes the normalizer rather than
competing with it. `dip` is included for that reason — it is already canonical and 2
recipes use it; inventing a rule that folds it into `appetizer` would reclassify working
data for no benefit.

**2. Delete the biscuit rule.** Remove `"biscuit": "dessert"` (`lib/normalizer.py:196`).
This is the root cause of the contaminated dessert bucket, and leaving it in place would
silently re-corrupt any recipe extracted after the cleanup runs. The one-off repair without
this deletion is a fix with a known expiry date.

**3. `scripts/reclassify_dish_type.py`.**

- Reads all recipes via `get_recipe_index(recipes_dir(), include_ingredients=True)`.
- Submits **one Batches API job** (239 requests, 50% cost). Each request carries the recipe
  name, its ingredient list, and its current `dish_type`.

  `custom_id` is the recipe's **index** (`r0`, `r1`, …), not its name: the field is
  restricted to alphanumerics, underscores, and dashes, and this library has names like
  `Arayes 🥙` and `Hardee's Biscuits` that cannot be used verbatim. The index maps back to
  the name through the ordered recipe list.
- Constrains output with `output_config.format` → `json_schema` whose `dish_type` property
  is an **`enum` of the 13 values**. An out-of-vocabulary answer is structurally
  impossible, so no post-hoc validation branch can drift from the vocabulary.
- Uses the `anthropic` SDK on `claude-opus-5`, matching the existing integration pattern
  in `lib/receipt_parser.py:31` / `lib/meal_suggester.py`.

  Two model-specific details the request must respect: `claude-opus-5` **thinks by
  default**, and `max_tokens` caps thinking *plus* response text together — so a
  classification returning ~20 tokens still needs real headroom (`max_tokens=2000`) or it
  truncates mid-thought. Effort is set to `low`; this is a one-field classification, not a
  reasoning task.
- **`--dry-run` is the default.** It prints a report grouped as `CHANGE` / `KEEP` /
  `UNRESOLVED` and writes nothing.
- **`--apply`** writes the new `dish_type` into recipe frontmatter following the existing
  backfill pattern exactly (`backfill_fit.py:63-68`):

  ```python
  updated = frontmatter.apply(content, {"dish_type": new_value}, ("dish_type",))
  if updated is None:          # note has no frontmatter — report, don't write
      return "no-frontmatter"
  create_backup(path)          # timestamped copy in .history/
  path.write_text(updated, encoding="utf-8")
  ```

  Passing `("dish_type",)` as `managed_keys` scopes the rewrite to that one key, so no
  other frontmatter field is touched. Every change is revertible from `.history/`.

**Error handling.** Batch results arrive in arbitrary order and are keyed by `custom_id`,
never by position. A recipe with no result — errored, expired, or canceled — keeps its
existing `dish_type` and is listed under `UNRESOLVED`. Nothing is silently skipped: a
recipe appears in exactly one of the three report sections, and the three counts sum to
239.

### Part 2 — `/cook-now` page and `GET /api/cook-now`

`lib/cook_now.generate()` already returns everything the page needs per recipe
(`recipe, image, have, total, coverage, missing, at_risk`). The work is a chip-group field,
an endpoint, and a template.

**1. Chip groups.** A `DISH_TYPE_GROUPS` mapping (in `lib/cook_now.py`) collapses the
13-value stored vocabulary into 6 UI groups:

| Chip | `dish_type` values |
|---|---|
| Mains | `main`, `sandwich`, `soup` |
| Breakfast | `breakfast` |
| Sides | `side`, `salad`, `bread`, `sauce` |
| Snacks | `snack`, `appetizer`, `dip` |
| Desserts | `dessert` |
| Drinks | `drink` |

The split keeps the stored data precise and the interface usable. A recipe whose
`dish_type` is missing or unrecognized maps to `Mains` — the filter must never make a
cookable recipe unreachable through a data gap.

**2. `GET /api/cook-now`.** Returns `cook_now.generate()`'s payload with a `group` field
added per recipe. Accepts the existing `limit` parameter. No filtering server-side.

**3. `/cook-now` page.** Renders through `_serve_page_with_claude_bar`. Chips filter
client-side from the single payload, so toggling is instant. **Desserts starts
deselected** — the chip stays visible in its off state with a "47 dessert recipes hidden"
line, so what is hidden is never a mystery. Selection persists in `localStorage`.

**4. Registration (CLAUDE.md invariant).** `/cook-now` takes no path parameters and no
required query parameters, so it is bookmarkable: it goes in `SECTIONS` in
`lib/web_dashboard.py`, and **not** in `NOT_BOOKMARKABLE`. Then propagate to both
consumers — `scripts/generate_web_dashboard.py`, and `scripts/sync_safari_bookmarks.py
--apply` (which quits and relaunches Safari; pre-authorized, no-ops if Safari isn't
running). Skipping the registration fails the existing test suite.

## Acceptance Criteria

- [ ] `--dry-run` reports a `CHANGE`/`KEEP`/`UNRESOLVED` split over all 239 recipes with no
      vault writes; counts sum to the recipe total.
- [ ] After `--apply`, every recipe's `dish_type` is one of the 12 vocabulary values.
- [ ] `Butter Biscuits` is no longer `dessert`; `Ham Cheddar + Chive Protein Biscuits` is no
      longer `biscuits`.
- [ ] Re-extracting a biscuit recipe does not classify it as a dessert.
- [ ] `/cook-now` loads with Desserts deselected and states how many recipes are hidden.
- [ ] Toggling a chip re-filters with no network request.
- [ ] `/cook-now` appears in the vault launcher note and in Safari bookmarks after the sync.
- [ ] `Cook Now.md` is byte-identical to before the change when regenerated from the same
      inventory.
- [ ] Full test suite green.

## Out of Scope

- Filtering the generated `Cook Now.md` note (stays a flat list).
- Sorting or filtering by anything other than meal type.
- Re-classifying `meal_occasion` (a separate, multi-valued field that is already clean).
- The unrelated consume-on-cook decrement defects found while investigating this
  (matcher misses, `ct`-vs-`cup` unit gap, silent success toast) — separate work.
